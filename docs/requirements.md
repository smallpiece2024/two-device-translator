# two-device-translator 要件定義

2つのデバイスを使い、それぞれ別の言語で話すと、相手のデバイス上で相手の言語に翻訳されてテキスト表示・発話される、対面向けのリアルタイム通訳ウェブサービス。見た目は2人でチャット（LINE風）をしているような画面。

> 本ドキュメントは要件定義であり、設計・実装の詳細は別途 `docs/design/` に定める。
> 技術検証用プロトタイプ [`simple-translator`](../../simple-translator)（Google Cloud STT/翻訳/TTS + Next.js + WebSocket、1ブラウザ内完結・ローカル専用）をベースに、2デバイス対応・認証・履歴永続化・AI機能を追加する。

---

## 1. 目的とスコープ

### 1.1 目的
- 異なる言語を話す2人が、それぞれ自分のデバイス・自分の言語で会話できるようにする。
- 発話は相手デバイスで相手言語に翻訳され、テキスト表示され、（トグルONなら）音声で発話される。
- 会話をチャット履歴として残し、オーナーが後から振り返れる。
- 会話を踏まえたAIアシスタント（雑談のきっかけ提供・終了時要約）を提供する。

### 1.2 本プロジェクトのスコープ
- Node.js（Next.js）によるウェブサービスとして実装する。
- ログインは必須（無償でも）。課金・有償プランは**将来検討**とし、今回は実装しない（プラン概念の器だけ用意）。
- 人数上限はプランの制限項目として設計に残すが、**今回は実質無制限**（実装上は1対1を基本形とする。§9参照）。

### 1.3 スコープ外（今回作らない）
- 課金・決済・有償プランの実際の課金処理。
- 3人以上（1対多, 1:N）の同時会話は**将来フェーズで対応**し、MVPでは1対1を対象とする（データモデル・ルーティングはN人拡張可能に設計する）。
- 完全な同時通訳（プロトタイプ同様、発話区切り単位の逐次通訳に近い体験とする）。
- ネイティブアプリ（iOS/Android アプリ）。ブラウザ（PWA含む可）で提供する。
- 管理者ダッシュボード等の運用管理UI。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| オーナー (Owner) | サービス契約者。ログインしてトークルームを作成・招待・終了できる主体。会話履歴を保有・閲覧できる。 |
| ゲスト (Guest) | オーナーに招待されて会話に参加する者。アカウント登録は不要。QRコードとクッキーで識別される。 |
| トークルーム (Room) | 1回の会話の場。オーナーが作成し、招待でゲストが参加する。 |
| 参加者 (Participant) | トークルームに在室しているユーザー（オーナー/ゲスト）。 |
| 発話区切り (Utterance) | 音声認識結果を確定させる単位。無音時間・文字数・経過時間・手動commit・stopで確定する。 |
| STT | Speech-to-Text（音声認識）。Google Cloud Speech-to-Text を使用。 |
| TTS | Text-to-Speech（音声合成・発話）。Google Cloud Text-to-Speech を使用。 |
| AIアシスタント | 会話内容を踏まえて話題提供・要約を行うLLM（Claude / OpenAI 切替可能）。 |

## 3. アクター

| アクター | 説明 |
|---|---|
| オーナー | ログイン、ルーム作成、QR招待、言語/名前/発話設定、会話、終了・再開、履歴閲覧、AIアシスタント利用。 |
| ゲスト | QR読込で参加、言語/名前/発話設定、会話。アカウントは持たない。 |

| 外部サービス | Google Cloud（STT/翻訳/TTS）、LLMプロバイダ（Claude/OpenAI）、認証（メール+PW / Google OAuth）。 |

## 4. システム全体構成

```text
[デバイスA: 話者]                                  [デバイスB: 聞き手]
  マイク入力(MediaRecorder)                          翻訳テキスト表示 + 翻訳音声再生
        │  音声チャンク                                     ▲
        ▼  (WebSocket)                                      │ (WebSocket)
┌───────────────────────────── アプリサーバー (Next.js + WebSocketサーバー) ─────────────────────────────┐
│  ルーム管理 / 参加者・話者識別(クッキー) / セッション / 発話区切り判定 / 配信ルーティング                 │
│        │                                                                                                  │
│   Google STT(Streaming) ──▶ 発話確定 ──▶ Google Translation(話者言語→各聞き手言語) ──▶ Google TTS        │
│        │                                                                                                  │
│   会話履歴の永続化(DB)  ／  AIアシスタント(Claude/OpenAI: 話題提供・要約)                                  │
└───────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

- **配信の基本フロー**: 話者デバイスのマイク音声 → サーバーでSTT → 発話確定 → 話者言語から各聞き手の言語へ翻訳 → 聞き手デバイスへテキスト配信＋（TTS ON時）音声配信。
- **表示の原則**: 各デバイスは会話全体を「そのデバイス利用者の言語」で表示する。自分の発話は原文、相手の発話は自分の言語への翻訳を表示する（LINE風。自分＝右、相手＝左）。
- **発話（音声再生）の原則**: 各デバイスは「相手の発話の翻訳音声」のみを再生する（自分の発話は再生しない）。TTSはトグルON時のみ。テキスト表示はトグルに関係なく常に行う。
- **セキュリティ境界**: Google Cloud / LLM の認証情報はサーバー側のみで保持し、ブラウザには一切渡さない（`NEXT_PUBLIC_` を付けない）。
- **ホスティング**: アプリサーバー（Next.js + WebSocketサーバー）は **GCE（Compute Engine）上で常時稼働**し、プロトタイプの WebSocket＋ストリーミングSTT 構成を流用して2デバイス対応に拡張する。**DB・認証は Supabase**。リアルタイム同期は GCE 上の自前 WebSocket で行う（Supabase Realtime は使用しない）。HTTPS はリバースプロキシ（Caddy/nginx + Let's Encrypt）で終端する。

## 5. 技術スタック

### 5.1 継承（プロトタイプ）
- フロントエンド: Next.js (App Router) / React / TypeScript、マイク入力=MediaRecorder API、通信=WebSocket、スタイル=CSS Modules（**Tailwind禁止**）。
- サーバー: Node.js / TypeScript、WebSocket=`ws`、メッセージ検証=zod。
- 音声処理: Google Cloud Speech-to-Text（**ストリーミング**）/ Translation / Text-to-Speech。
- 発話区切りロジック（初期値: 無音1.0秒 / 確定80文字 / 同一発話10秒 / 手動commit / stop、設定で変更可）。
- テスト: Jest（単体・結合）+ Playwright（E2E）。

### 5.2 新規追加
- **認証**: **Supabase Auth** を採用。オーナーはメール+パスワードと Google OAuth でログイン（Google 連携の具体設定は実装側に一任）。ゲストは署名付きクッキーによる匿名識別。
- **DB**: **Supabase（PostgreSQL）** に 会話履歴・アカウント・ルーム・招待を永続化。アクセスは supabase-js（Row Level Security）、スキーマ/マイグレーションは Supabase CLI で管理。
- **リアルタイム同期**: 2デバイス間のメッセージ配信は **GCE 上の自前 WebSocket サーバー**で行う（Supabase Realtime は使用しない）。
- **ホスティング**: **GCE（Compute Engine）VM** に Next.js + WebSocket サーバーを常時稼働（プロセス管理は pm2/systemd 等）。リバースプロキシ（Caddy/nginx）＋ Let's Encrypt で HTTPS を提供する。
- **AIアシスタント**: LLMプロバイダ抽象化レイヤ（Claude / OpenAI を環境変数で切替）。サーバー側から呼び出す。
- **QRコード**: ルーム参加URLのQR生成（サーバー/クライアントいずれかで生成）。

### 5.3 GCP認証情報の扱い
- 開発時: ローカルの Application Default Credentials（`gcloud auth application-default login`）を継承。
- 本番想定: サービスアカウント運用に切替可能とする（設計で吸収）。

## 6. 機能要件（FR）

### FR-1 認証・アカウント（オーナー）
- FR-1.1 オーナーは メール+パスワード または Google OAuth でログインできる。
- FR-1.2 未ログインではルーム作成・履歴閲覧・AI機能を利用できない。
- FR-1.3 オーナーは個人設定として「デフォルトで使用する言語」を保存できる。

### FR-2 トークルームと招待（QR）
- FR-2.1 オーナーはログイン後、トークルームを作成できる。
- FR-2.2 オーナーはルームの参加用QRコードを生成・表示できる。
- FR-2.3 ゲストは自分の端末でQRを読み込み、（アカウント登録なしで）ルームに参加できる。
- FR-2.4 参加時、サーバーはゲストデバイスに署名付きクッキーを付与し、以後そのクッキーで同一ゲストを識別する。
- FR-2.5 招待できるゲスト数の上限はオーナーのプラン制限に従う（今回は無制限。MVPは1対1、将来は1対多(1:N)）。

### FR-3 話者識別
- FR-3.1 システムは、クッキー（およびルーム内の参加者情報）により、発話がどの参加者のものかを識別する。
- FR-3.2 一時的な通信断からの再接続時、同一クッキーであれば同一参加者として復帰できる。

### FR-4 言語設定
- FR-4.1 各参加者は自分が話す言語を、プルダウン等で手動選択できる。
- FR-4.2 デフォルト言語は、オーナー=個人設定の言語、ゲスト=英語。
- FR-4.3 **言語検出モード**: 通常は各参加者の選択済み（デフォルト）言語で固定する。デフォルトと異なる言語で話したいときにユーザーが検出モードを有効にして発話すると、Google STT の複数言語候補指定で言語を判定し、話者の言語として設定する。判定後は再びその言語で固定し、会話中の常時再判定は行わない。
- FR-4.4 対応言語はMVPで日本語・英語（ja-JP / en-US）とし、言語追加が可能な構成にする。

### FR-5 名前設定
- FR-5.1 各参加者は任意で表示名を設定できる（未設定でも会話可能）。

### FR-6 発話（TTS）ON/OFF
- FR-6.1 各参加者は自分のデバイスの発話（TTS）をトグルでON/OFFできる。
- FR-6.2 発話がOFFでも、翻訳テキストの表示は常に行われる。

### FR-7 リアルタイム音声翻訳（コア）
- FR-7.1 参加者が発話すると、その音声はサーバーでSTTされる。
- FR-7.2 発話区切りで確定したテキストを、話者言語から各聞き手の言語へ翻訳する。
- FR-7.3 翻訳結果を聞き手デバイスに配信し、テキスト表示する。
- FR-7.4 聞き手デバイスのTTSがONなら、翻訳テキストを音声合成して再生する。
- FR-7.5 認識途中（interim）のテキストは話者デバイスに淡色表示してよいが、翻訳・音声合成は確定発話のみを対象とする（プロトタイプ方針を継承）。
- FR-7.6 手動での発話区切り（commit）と停止（stop）ができる。

### FR-8 チャットUI（LINE風）
- FR-8.1 会話はチャットのタイムラインとして表示する（自分=右、相手=左、話者名・時刻付き）。
- FR-8.2 各デバイスは会話全体をそのデバイス利用者の言語で表示する（自分の発話は原文、相手の発話は翻訳）。
- FR-8.3 ルームに入ると、両デバイスとも発話待機状態になる。

### FR-9 会話履歴の保存・振り返り
- FR-9.1 会話（発話テキスト・翻訳テキスト・話者・言語・時刻）をDBに永続化する。
- FR-9.2 オーナーは後日、自分のルームの会話履歴を閲覧できる。
- FR-9.3 会話履歴の永続閲覧はオーナーのみとする。ゲストには履歴への永続的な閲覧手段を設けない（ただし終了時要約は FR-11.3 に従いその場で表示する）。

### FR-10 AIアシスタント
- FR-10.1 オーナーのデバイスにAIアシスタント表示領域を設ける。
- FR-10.2 AIアシスタントは会話内容を踏まえ、雑談のきっかけとなる話題・質問案を提示する（例: 会話から判明した互いの母国について質問する提案）。
- FR-10.3 AIプロバイダ（Claude / OpenAI）は設定で切替可能とする。
- FR-10.4 話題提供は**オーナーのボタン操作によるオンデマンド取得を基本**とする（無音で自動的にAIを呼ぶことはせず、トークンコストを予測可能にする）。ただし**一定時間会話がない場合は、話題提供ボタンを強調表示してオーナーに利用を促す**（AI呼び出しはボタン押下時のみ）。アイドル時間のしきい値は設定可能とする。

### FR-11 終了時要約
- FR-11.1 会話終了時、AIが会話全体の要約テキストを生成して表示する。
- FR-11.2 要約は履歴とともに保存され、オーナーは後から閲覧できる。
- FR-11.3 終了時の要約は、終了時点で**両者（オーナー・ゲスト）の画面に表示**する。ゲストへの永続的な閲覧手段は設けない。

### FR-12 利用終了・再開・不在検出
- FR-12.1 オーナーが明示的に終了すると、ゲストは強制的に終了となる。
- FR-12.2 一時的な不在（通信断）と終了を区別する。長時間1人だけの在室が続く場合は自動終了とする（しきい値は設定可能）。
- FR-12.3 オーナーが同じルームに再入室し、再度QRで招待すると会話を再開できる。ゲストデバイスにクッキーが残っていれば、再開前の参加者として識別する。

### FR-13 プラン・人数上限（器のみ）
- FR-13.1 プランごとの「ルーム参加可能人数上限」を設定として持つ（無償=オーナー含め2人、有償=無制限 などを想定）。
- FR-13.2 今回は上限を実質無制限として扱い、課金処理は実装しない。

### FR-14 発話の取り消し（STT誤認識の撤回）（bd-652 実機テストでの気づきから追加、Phase2で実装）
- 背景: STTが発話を誤認識した場合、誤ったテキストがそのまま翻訳・配信され、相手には誤認識だと伝わらず、終了時要約（FR-11）にも影響する。
- FR-14.1 話者は自分の確定発話（メッセージ）を事後に「取り消し」できる。取り消しは相手に「この発話は無かったこと（誤認識）」として伝わる。
- FR-14.2 取り消しは**トグル式**とし、誤って取り消した場合は同じ操作でもう一度実行すると復元できる（取り消し⇄復元）。
- FR-14.3 取り消されたメッセージは、両デバイスで**打ち消し線＋取り消し済みであることが分かる表示**にする（バブルは削除しない。本文は残す）。
- FR-14.4 操作方法: モバイルは自分のバブルを**スワイプで即取り消し**（もう一度スワイプで復元）。PCは自分のバブルに**ホバーで×ボタン**を表示して取り消し（取り消し済みバブルでは同様の操作で復元）。
- FR-14.5 取り消し対象は自分の発話のみ。他参加者の発話は取り消せない（サーバー側で検証する）。
- FR-14.6 取り消し時、相手側でまだ再生されていないTTS音声（再生キュー内）はスキップする。すでに再生中の音声は中断しない。復元してもTTSは再生し直さない。
- FR-14.7 取り消し済みメッセージは、終了時要約（FR-11）およびAIアシスタントの話題提供（FR-10）の入力から除外する。会話履歴（FR-9）には取り消し状態も含めて保存し、履歴閲覧時も取り消し済み表示を維持する。

## 7. 非機能要件（NFR）

### NFR-1 セキュリティ・プライバシー
- NFR-1.1 マイク入力（`getUserMedia`）はセキュアコンテキストを要求するため、ローカルホスト以外では**HTTPS必須**。デプロイ先の **GCE 上でリバースプロキシ＋Let's Encrypt により HTTPS を提供**する。開発初期のローカル実機確認には開発トンネル（cloudflared/ngrok 等）を用いてよい。
- NFR-1.2 Google Cloud / LLM の認証情報はサーバー側のみで保持し、クライアントへ渡さない。
- NFR-1.3 ゲスト識別クッキーは署名付き・HttpOnly・Secure とする。
- NFR-1.4 音声データはリアルタイム処理にのみ用い、**音声そのものは永続保存しない**。永続化対象はテキスト（原文・翻訳）と要約のみとする。
- NFR-1.5 パスワードはハッシュ化して保存する（Credentials 認証で登録する場合）。

### NFR-2 パフォーマンス（体験）
- NFR-2.1 発話確定から相手デバイスでの翻訳表示までの遅延を、体感で会話が成立する範囲に抑える（目標値は設計・計測で定義）。
- NFR-2.2 翻訳は低遅延な専用API（Google Translation）を用い、AI機能（要約・話題提供）とは別系統で動かして会話のテンポを損なわない。

### NFR-3 可用性・回復性
- NFR-3.1 WebSocket切断時に自動再接続を試みる。
- NFR-3.2 再接続時、クッキーにより同一参加者としてルームに復帰できる。

### NFR-4 対応環境
- NFR-4.1 対象ブラウザは Chrome / Edge / Safari の最新版（PC・モバイル）を想定。モバイル（特にiOS Safari）での動作を確認対象とする。
- NFR-4.2 音声認識はブラウザのWeb Speech APIに依存せず、サーバー経由のGoogle STTで行うため、ブラウザ差異の影響を受けにくい構成とする。

### NFR-5 保守性
- NFR-5.1 言語・AIプロバイダ・DBは差し替え可能な抽象を設ける。
- NFR-5.2 発話区切り等のしきい値は設定で調整可能にする。

## 8. データモデル（概要）

正式なスキーマは `docs/design/` で定義。要件レベルの主要エンティティは以下。

- **User（オーナー）**: id, email, 認証情報（PWハッシュ or OAuth）, 既定言語, プラン, 作成日時。
- **Room（トークルーム）**: id, ownerUserId, 状態（active/ended）, 参加人数上限, 作成/終了日時。
- **Participant（参加者）**: id, roomId, 種別(owner/guest), guestCookieId, 表示名, 言語, TTS ON/OFF, 在室状態。
- **Message（発話）**: id, roomId, participantId, 原文, 原文言語, 翻訳（言語ごと）, 時刻。
- **Summary（要約）**: id, roomId, 本文, 生成日時。
- **Invite（招待）**: id, roomId, トークン, QR対象URL, 有効期限。

## 9. 開発フェーズ（段階開発）

### Phase 1: コア翻訳（2デバイス間のリアルタイム通訳）
- 目的: 「Aで話すとBに相手言語で表示・発話される」双方向翻訳が2台で動くことを最優先で確認する。
- 含む: ルーム作成（簡易・URL/ID共有でも可）、2デバイスのWebSocket参加、STT→翻訳→配信→TTS、言語の手動選択、LINE風チャット表示、発話ON/OFFトグル。
- 対象言語: ja ⇔ en。
- 認証: 最小限（この段階では省略または簡易でよい）。

### Phase 2: 認証・ルーム・QR招待
- 含む: オーナーの メール+PW / Google ログイン、正式なルーム管理、QRコード招待、ゲストのクッキー識別、名前設定、自動言語検出、プラン/人数上限の器、終了・再開・不在検出、発話の取り消し（FR-14）。

### Phase 3: AI・履歴・要約
- 含む: 会話履歴の永続保存とオーナーの振り返り画面、AIアシスタント（話題提供）、終了時要約、再開時のゲスト識別復元、プロバイダ切替（Claude/OpenAI）。

## 10. 前提・制約

- プロトタイプ [`simple-translator`](../../simple-translator) の技術方針（Google Cloud 3サービス / Next.js / WebSocket / CSS Modules / zod / 逐次通訳寄り）を継承する。
- 翻訳・TTSは確定した発話区切り単位で行う。interim は表示のみ。
- 対応言語はMVPで日本語・英語。将来的に拡張可能な構成とする。
- 低遅延化よりも自然に意味が通る翻訳を優先する方針を継承しつつ、会話成立に必要な遅延は計測して管理する。
- Windows環境でのローカル起動手順・GCP認証・HTTPS化手順をREADMEに記載する。

## 11. 確定事項（残論点の決定記録）

当初の残論点8件は以下のとおり確定した。各項は本文の該当FR/NFRにも反映済み。

| # | 論点 | 決定 | 反映先 |
|---|---|---|---|
| ① | 配信・デプロイ / リアルタイム通信 | **GCE（Compute Engine）にデプロイ**（e2-micro 無料枠〜e2-small 約$13/月）。**プロトタイプの WebSocket＋ストリーミングSTT 構成を流用**して2デバイス対応に拡張。リアルタイム同期は GCE 上の自前 WebSocket、**DB・認証は Supabase**。HTTPS はリバースプロキシ＋Let's Encrypt。（比較検討: Vercel+Supabase はゼロ運用だが、発話単位バッチSTTへの作替と Hobby の非商用制限のため見送り。） | 4, 5, 9, NFR-1.1 |
| ② | 言語検出モード | **通常は各参加者の選択済み（デフォルト）言語で固定**。デフォルトと異なる言語で話したいときにユーザーが検出モードを有効にして発話すると、Google STT の複数言語候補指定で言語を判定・設定する。会話中の常時再判定はしない。 | FR-4.3 |
| ③ | DB | **Supabase（PostgreSQL）** に永続化。アクセスは supabase-js（RLS）、スキーマは Supabase CLI。 | 5.2, 8 |
| ④ | 認証基盤 | **Supabase Auth** を採用。オーナーはメール+パスワードと Google OAuth でログイン（Google 連携の具体設定は実装側に一任）。ゲストはクッキー識別。 | 5.2, FR-1.1 |
| ⑤ | AI話題提供のトリガー | **オンデマンド（オーナーのボタン）を基本**（無音で自動的にAIは呼ばない）。**一定時間会話がない場合は話題提供ボタンを強調表示して利用を促す**。アイドルしきい値は設定可能。 | FR-10.4 |
| ⑥ | 音声データ保持 | **音声は永続保存しない**。永続化対象はテキスト（原文・翻訳）と要約のみ。 | NFR-1.4 |
| ⑦ | 履歴/要約の閲覧 | **会話履歴の永続閲覧はオーナーのみ**。**終了時要約は終了時点で両者（オーナー・ゲスト）の画面に表示**（ゲストへの永続閲覧手段は設けない）。 | FR-9.3, FR-11.3 |
| ⑧ | 参加人数 | **MVPは1対1**（オーナー1＋ゲスト1）。**最終的に1対多（1:N, オーナー1＋ゲスト複数）へ段階的に拡張**。データモデルとルーティングはN人拡張可能に設計する。 | 1.3, 8 |

> 上記はすべて確定事項。設計・実装過程で見直す場合は本表を更新する。
